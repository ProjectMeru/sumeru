Sumeru — addon layout and XML reference
=========================================

The `addons/` directory at the project root holds installable app modules
(kernel addon **`base`** lives at **`addons/base/`**).

Directory (technical name = folder name, should match manifest "name"):
  addons/<technical_name>/
    manifest.json     — required
    init.go           — package + models blank import only (see Go layout below)
    README.md         — recommended; purpose, models, key files
    models/           — Go structs embedding sdk.Model with sumeru:"model=…" tags. Run make generate so models/zmodels.go calls sdk.MustRegister (do not RegisterModel in init). Import sumeru/core/sdk.
    security/
      security.xml    — groups, categories (load first in manifest)
      sys.access.csv  — ACL rows (auto-loaded; optional in manifest data for docs)
    data/             — optional seed XML (noupdate="1" where appropriate)
    views/
      actions.xml     — window actions via <action type="window"> (preferred)
      *_actions.xml   — optional split when many actions (e.g. core_company_actions.xml)
      {model}_{type}_views.xml — one primary view per file (e.g. core_partner_form_views.xml)
      {model}_inherit_views.xml — view xpath inherits (after base views in manifest)
      menus.xml       — always load last in manifest
    hooks.go          — optional; event subscriptions, render hooks (not in init.go)
    {feature}.go      — optional public API (e.g. mail/mail.go, automation/actions.go)
    static/           — optional CSS/assets

Reference layout: addons/contacts/ (gold standard for new addons)

Core ships:
  addons/base/              — kernel `base` sys.module (Go models + XML)
  core/sdk/                 — stable Go facade for addons (import sumeru/core/sdk)
  core/sdk/platformmsg/     — shared log/HTTP strings (import sumeru/core/sdk/platformmsg)
  core/module/addon_template/ — manifest template + this reference (MODULE_STANDARD.txt)

manifest.json keys
------------------
  name           string   — technical module name (unique), equals folder name
  display_name   string   — optional; human app title in Apps and shell (e.g. "Companies"); defaults from name
  version        string   — semantic version string
  depends        []string — list of technical names; "base" is the core module
  author         string
  description    string  — shown in Apps
  application    bool     — optional; default true. false = hidden from Apps cards (e.g. base)
  data           []string — paths relative to addon root; XML load order is list order

manifest.json data load order (recommended)
-------------------------------------------
  1. security/security.xml
  2. security/sys.access.csv (optional; auto-loaded if omitted)
  3. data/*.xml (seed records)
  4. views/actions.xml and views/*_actions.xml
  5. views/*_{form,list,kanban,...}_views.xml (base views before inherits)
  6. views/*_inherit_views.xml
  7. views/menus.xml (always last)

File and XML id naming
----------------------
  View files:     {model_underscores}_{type}_views.xml   e.g. core_partner_form_views.xml
  View xml id:    view_{model_underscores}_{type}       e.g. view_core_partner_form
  Action files:   actions.xml or {area}_actions.xml
  Action xml id:  action_{short_name}                   e.g. action_contacts
  Window actions: prefer <action type="window" id="..." model="..." name="..." view_mode="..."/>
                  over raw <record model="sys.action.window"> (both supported; shorthand is standard)

Go layout
---------
  init.go — package declaration + blank import of models only:
    import _ "sumeru/addons/<name>/models"
  hooks.go / feature.go — event.Subscribe, render.RegisterShellHook, server action runners, etc.
  Do not put hook registration in init.go when models/ exists; keeps init.go minimal and readable.

ACL CSV (sys.access)
--------------------
  Model access rules load from security/sys.access.csv (or sys.access.csv at the addon root)
  automatically during module sync. Listing the CSV in manifest data is optional and is not
  parsed as XML (manifests may still include it for documentation only).

Multiple addon roots (sumeru.conf)
----------------------------------
  addons_path = addons,/opt/sumeru/extra-addons
  Paths are scanned in **`addons_path`** order. Later roots override duplicate module names.
  If the same module name appears in two roots, the **later** path wins (override).

Module XML (standard)
---------------------
  **Root element (required):** `<sumeru>` — wraps all module data records for the Sumeru loader.

  **File header (recommended):** `<?xml version="1.0" encoding="utf-8"?>` on the first line.

  **`<data>` (recommended):** Wrap module content in `<data>...</data>` (Sumeru-style). Optional **`noupdate="1"`** (or `true` / `yes`) on `<data>` for records that should not be overwritten on module update; parsed into ViewList/MenuList.NoUpdate (reserved for future skip-on-upgrade behavior).

  **`<record>`** — `id`, `model`; children `<field name="..."`:
    - Body text → field value
    - `ref="module.xml_id"` → Many2one / reference (highest precedence)
    - `eval="True"` | `eval="[(6,0,[])]"` etc. → stored as literal string (no code execution)

  **`<menuitem>`** — `id`, `name`, `parent`, `action`, `sequence`, `web_icon`. The `name` value is stored in **`sys.menu.name`** (globally unique): use distinct labels across all modules (e.g. "All Companies" vs root "Companies").

  **`<view>`** (inline in data files) — `id`, `model`, `type` (`form` | `list` | `kanban` | `pivot`); inner tags match arch below. Use **`type="list"`** for list views (file: `views/list_view.xml`, id suffix `_list`).

  **View arch in `sys.view` (stored `arch` column)** — root may be:
    - **`<view type="form">...</view>`** (native), or
    - **`<form>...</form>`**, **`<list>...</list>`**, **`<kanban>...</kanban>`** (alternate roots).

  **Form arch tags (supported):**
    `<header>` — `<button name string type class/>`, `<field widget="statusbar"/>`
    `<sheet>` — `<div class>`, `<group string>`, `<field/>`, `<notebook><page string>` with fields/groups,
                `<separator string=""/>` (or empty), `<label for="" string=""/>`
    `<footer>` — `<button/>`
    `<chatter>` — thread + composer on workspace forms (requires a record id); messages stored in **`mail.message`** (see Activity and mail logging below).

  **List view:** `<field name string/>` columns (`type="list"`; `list` in `view_mode` opens this view). Optional **`open="false"`** (or `0`, `off`, `no`) on `<list>` or `<view type="list">` disables opening the form when a row is clicked; omitted or `true` opens the form (default).

  **Kanban:** `<field/>` cards (simplified layout).

  **Tags in data files — not executed by the loader (ignored unless modeled above):**
    `<template>`, `<function>`, `<delete>` — prefer explicit `<record>` definitions.

  **Interleaving note:** Within one `<group>`, children are rendered in blocks (separators/labels, then fields, then subgroups); split into nested `<group>`s if order matters.

View inheritance
----------------
  Use <record model="sys.view"> with:
    <field name="inherit_id" ref="module.xml_id_of_parent_view"/>
    <field name="arch" type="xml"> ... </field>
  Parent must be an sys.view already loaded (e.g. from a dependency module listed before this file in manifest "data").

  If inherit_id cannot be resolved (parent module not installed, wrong ref, or stale DB), the
  platform logs a line using the format in core/sdk/platformmsg/messages.go (FmtViewInheritWarning).
  Declare every parent module in manifest "depends" and install dependencies before relying on inherits.

  Supported xpath targets: //field[@name='field_name'] with position one of:
    after, before, replace, inside
  Stored arch may use `<form>`/`<list>` roots or `<view>`; both load after merge.

  Example: addons/contacts/views/core_partner_form_inherit_views.xml (xpath after phone → customer_rank)

Model inherit
-------------
  Extend an existing ORM model from a dependent module with a Go struct that embeds sdk.Model
  and uses inherit= instead of model=:

    type PartnerContacts struct {
        sdk.Model `sumeru:"inherit=core.partner"`
        CustomerRank sdk.Integer `sumeru:"string=Customer Rank,default=0"`
    }

  Rules:
    • inherit= and model= are mutually exclusive on one struct
    • Target model must register first (manifest depends + import order)
    • Duplicate field names on the same model panic at startup
    • Run make generate, then -u your_module for additive schema sync on extended models
    • Pair with view xpath inherit to show new fields in the UI

  Example: addons/contacts/models/partner_extend.go

Strict convention (enforced on startup)
-----------------------------------------
  Every addon under addons_path must:
    • Folder name = manifest "name", matching ^[a-z][a-z0-9_]*$
    • manifest.json: name, version, author, description, data (array; empty [] allowed)
    • init.go at addon root with `package <name>` matching manifest name
    • If models/*.go exists (non-_test): init.go must blank-import `_ "<module>/…/models"` for that addon
    • Every manifest data file must exist; each .xml must use root element <sumeru>
  Violations cause LoadAddonPaths / server startup to fail with a clear error.

Go registration (zero-edit)
----------------------------
  Do not edit cmd/sumeru/main.go for new addons. Run `go generate ./cmd/sumeru` or `make generate`
  (or `make run` / `make build`, which run generate first). This refreshes cmd/sumeru/zimports.go
  with blank imports for every strict addon discovered via sumeru.conf addons_path.

External workspace: sumeru + sumeru_custom_addons
------------------------------------------------
  Standard code lives in the **`sumeru`** Go module. Client-specific runners can use a
  sibling **`sumeru_custom_addons`** tree (own go.mod, `replace sumeru => ../sumeru`) so
  generated blank imports are **not** written into **`sumeru/`**: run
  `go run ../sumeru/cmd/sumeru-import-gen` with **`-root`** pointing at the standard repo,
  **`-package addonimports`** (or another `[a-z][a-z0-9_]*` name), and **`-out`** set to an
  **absolute** path under **`sumeru_custom_addons`** (relative `-out` is resolved against
  `-root`, not the cwd). See **`sumeru/README.md`** and **`sumeru_custom_addons/README.md`**.
  Addons under **`sumeru_custom_addons/addons/<name>/`** use module path **`sumeru_custom_addons/addons/<name>`**
  for blank imports; addons under **`sumeru/addons/`** use **`sumeru/addons/<name>`**. The
  loader validates each addon against the **`go.mod`** that contains its directory.

Scaffold (bp)
-------------
  From repo root: `make bp NAME=my_module`  or  `go run ./cmd/sumeru-bp -name my_module`
  Scaffold always writes models/, views/ (including list_view.xml), and security/.
  Then: `make generate` (or `go generate ./cmd/sumeru`) and install with -i as usual.
  Custom workspace: `cd sumeru_custom_addons && make new MODULE=my_module`.

After adding a new addon, restart the server and install the module from /web/apps.

Activity and mail logging (Go)
------------------------------
XML data files cannot run Go code, so there is no Sumeru-style automatic `message_post` from static `<record>` rows alone. After a successful mutation in your own Go code (services, HTTP handlers, cron, and so on): use **`sumeru/addons/mail`** and **`mail.PostMessage(...)`** with **`mail.SubtypeComment`** for user-to-user chatter on a record, or **`mail.SubtypeNotification`** for record-level system notes (shown in the activity panel). **`mail.message`** is for that chatter and notifications only. For module install / uninstall / activate / update audit lines, call **`mail.LogModuleEvent(ctx, moduleName, verb, detail)`** (writes **`app.log`** via **`orm.AppendAppLog`**) or import **`sumeru/core/orm`** and **`orm.AppendAppLog`**. The stock server posts module events via **`mail.LogModuleEvent`**, record saves as notifications, and chatter posts as comments. Addons should follow the same pattern from their Go hooks rather than expecting XML to intercept ORM writes.

Server CLI
----------
  go run ./cmd/sumeru -- -c sumeru.conf -i mod1,mod2          # install modules
  go run ./cmd/sumeru -- -c sumeru.conf -u mod1,mod2          # update / reload XML for installed modules
  go run ./cmd/sumeru -- -c sumeru.conf -i sales --stop-after-init   # install then exit (no HTTP)

Branding outside core
---------------------
  1) Default shell colors and typography: edit **`core/engine/assets/css/sumeru-theme.css`** only (design tokens on `:root`). Load order is defined in **`core/engine/assets/stylesheets.go`** (`DefaultStylesheetURLs`).
  2) Optional per-addon overrides: add **`static/css/theme-overrides.css`** in the addon tree (override `:root` custom properties); the server serves it as **`/static/addon-css/<module>.css`** after the core sheets.
  3) Site-wide extra rules: set **`brand_css`** in sumeru.conf to a file path; it is linked as **`/static/brand.css`** after core and addon theme sheets.
